# Optional 3MF adapter

This directory is deliberately outside `lens_cap_pipeline` and its Skills/CLI
core. It is a small, auditable bridge for installations that have an external
CAD or slicer executable. It does not copy or inspect a user-supplied 3MF
archive beyond the package structure needed for validation.

## Routes

`three_mf_adapter.py standard INPUT.stl OUTPUT.3mf` writes a minimal 3MF Core
package using only Python's standard library (`zipfile`, `struct`, and XML
text). The ZIP entry order and timestamps are fixed, and the input is expected
to be a closed/manifold triangle mesh. For an externally generated assembly
whose STL contains known coincident/internal faces, `--drop-degenerate
--allow-nonmanifold` can be used explicitly; the manifest then records every
discarded facet and the boundary/non-manifold edge counts, and the result must
be treated as a topology-audit artifact rather than proof of printability.
This route is byte-stable for the same STL, title, Python, and zlib
implementation. It is a model package, not a slicer project: it contains no
printer profile or G-code.

`three_mf_adapter.py bambu INPUT.stl OUTPUT.3mf --mode export` resolves Bambu
Studio from `$PATH`, `BambuStudio`, or the macOS app bundle and runs its
headless `--export-3mf` command. Use `--mode slice` with full machine, process,
and filament JSON profiles to embed G-code:

```sh
python3 tools/3mf_adapter/three_mf_adapter.py bambu model.stl model-bambu.3mf \
  --mode slice \
  --machine-profile "/path/to/machine.json" \
  --process-profile "/path/to/process.json" \
  --filament-profile "/path/to/filament.json"
```

SCAD input is accepted by the same command. The adapter first invokes
OpenSCAD with `--backend Manifold` and passes the resulting temporary STL to
Bambu Studio. Every Bambu run writes `<output>.manifest.json` containing input
hash, tool banner, normalized command, exit status, output hash, and package
checks.

`three_mf_adapter.py openscad INPUT.scad OUTPUT.3mf` is the native OpenSCAD
route. It asks OpenSCAD to write a Core 3MF directly with the Manifold backend,
which preserves the boolean-unioned assembly and avoids flattening coincident
STL faces. The resulting package is still unsliced (no printer profile or
G-code); pass it to the Bambu route when a printer-specific project is needed.
Its sidecar records the OpenSCAD version and command in the same format as a
Bambu run.

`three_mf_adapter.py fixture DIR` creates a tiny 20 mm closed cube STL and a
deterministic Core 3MF. `--bambu --mode slice` additionally exercises the
Bambu route (profiles are required for slice mode). The cube is generated by
the script itself; no third-party or user model is included. The checked-in
`fixtures/fixture-cube-openscad.3mf` is the corresponding native OpenSCAD
smoke output (unsliced), while `fixtures/fixture-cube-bambu-sliced.3mf` is the
current printer-project smoke output with embedded G-code. Its adjacent
manifest records the exact profile input/post-run hashes, resolved inheritance
chains, effective project-settings audit, and semantic slice audit.

`verify INPUT.3mf` checks ZIP CRCs, required Core parts, parseable package and
model XML, object/component references, and mesh index bounds. With
`--require-slice`, it additionally requires one ordered Bambu G-code block,
matching MD5/config/project metadata, monotonic Z layers, at least one extrusion
path per layer, and non-degenerate XY motion/range/diversity compatible with the
model envelope; a tiny forged text member is not accepted as a slice.

Commands used for the smoke run (paths are intentionally machine-local and
are not required by the repository):

```sh
python3 tools/3mf_adapter/three_mf_adapter.py fixture /tmp/lenscap-fixture
python3 tools/3mf_adapter/three_mf_adapter.py verify \
  /tmp/lenscap-fixture/fixture-cube-standard.3mf

# Native OpenSCAD Core export (no slicer metadata):
python3 tools/3mf_adapter/three_mf_adapter.py openscad \
  tools/3mf_adapter/fixtures/fixture-cube.scad \
  /tmp/lenscap-fixture/fixture-cube-openscad.3mf
python3 tools/3mf_adapter/three_mf_adapter.py verify \
  /tmp/lenscap-fixture/fixture-cube-openscad.3mf

# Bambu Studio 02.08.02.60, A1 mini 0.2 nozzle profiles shipped in the app:
python3 tools/3mf_adapter/three_mf_adapter.py bambu \
  /tmp/lenscap-fixture/fixture-cube.stl \
  /tmp/lenscap-fixture/fixture-cube-bambu-sliced.3mf \
  --mode slice \
  --machine-profile "/Applications/BambuStudio.app/Contents/Resources/profiles/BBL/machine/Bambu Lab A1 mini 0.2 nozzle.json" \
  --process-profile "/Applications/BambuStudio.app/Contents/Resources/profiles/BBL/process/0.10mm Standard @BBL A1M 0.2 nozzle.json" \
  --filament-profile "/Applications/BambuStudio.app/Contents/Resources/profiles/BBL/filament/Bambu PLA Basic @BBL A1M 0.2 nozzle.json"
```

The sliced fixture contains `Metadata/plate_1.gcode`; Bambu Studio reports it
as a manifold, 20 × 20 × 20 mm, one-part object. The current manifest
binds the three profile files before and after the run, records every inherited
profile hash, and shows `effective_profile_audit=passed`. Its semantic G-code
audit records 200 declared and 200 extrusion-bearing layers at 0.10 mm, 13,438
positive XY extrusion moves, matching G-code MD5/config/project metadata, and
path range/diversity consistent with the model bounds. It is therefore the
current retained slice smoke artifact, subject to the local printer/profile and
preview caveats below. All three of
`fixture-cube-standard.3mf` (portable Core-only),
`fixture-cube-openscad.3mf` (native OpenSCAD Core export), and
`fixture-cube-bambu-sliced.3mf` (a real Bambu project with embedded G-code)
are retained under `fixtures/`, with sidecar manifests recording the checks.
A recorded native fixture snapshot's exact SHA-256 is in its sidecar manifest.
The adapter removes the volatile creation date, replaces generated UUIDs with
content-derived UUIDv5 values, and canonicalizes ZIP entry order/metadata, so
same-toolchain reruns are byte-stable. Another OpenSCAD/Python/zlib release may
still tessellate or compress differently; compare the recorded semantic audits
across versions rather than assuming identical bytes.
A Bambu slice may be regenerated locally with the command above; Bambu
embeds random UUIDs, rendered PNGs, dates, and release-dependent G-code
metadata, so its bytes are not promised to be identical across runs even with
identical input.

The ImageGen v3 fixture's retained `*-bambu-project.3mf.manifest.json` is the
current multipart **export-mode** counterpart: it records the same profile
hash/inheritance/effective-settings contract but deliberately contains no
G-code. Older Helios v1/v2 and Mamiya `*-bambu-slice.3mf` files are historical
compatibility snapshots whose sidecars predate these audits; do not use their
G-code presence or byte counts as current release evidence.

Sidecar paths are deliberately portable: files inside this checkout are
relative to its root, app-bundle executables are shown as `<BambuStudio.app>`
or `<OpenSCAD.app>` (including app-relative resource/profile suffixes), and
other external files retain only a `<external>/basename` placeholder. SHA-256
values and command options remain available for provenance without embedding a
developer's home directory.

Suggested local/CI checks (the standard route needs no optional package):

```sh
python3 -m py_compile tools/3mf_adapter/three_mf_adapter.py
python3 tools/3mf_adapter/three_mf_adapter.py fixture /tmp/lenscap-3mf-check
python3 tools/3mf_adapter/three_mf_adapter.py verify \
  /tmp/lenscap-3mf-check/fixture-cube-standard.3mf
unzip -tqq /tmp/lenscap-3mf-check/fixture-cube-standard.3mf
```

When OpenSCAD is installed, also run the native command shown above and use
the local slicer's `--info` command to confirm the expected bounds and
manifold status. On this host, OpenSCAD 2026.06.12's native Helios assembly
exports were each reported by Bambu Studio as one part with `manifold = yes`;
the STL-flattened Core conversions intentionally retain their separate
topology audit. Bambu slicing is an optional integration check and should be
asserted with `verify --require-slice` plus `unzip -tqq`, not by assuming that a
zero process exit code proves physical fit.

## Limitations

* A valid ZIP/Core package is not proof of physical fit, printer compatibility,
  or a successful real-world print.
* Bambu Studio's command-line behavior and profile schema vary by release;
  profile paths must be supplied from the local installation.
* Native OpenSCAD export requires a local OpenSCAD build with the Manifold
  backend; its XML metadata and UUIDs can vary by release even when geometry
  is unchanged.
* The standard writer accepts STL only and intentionally omits colors,
  slicer/project extensions, and multi-material assignments.
* The adapter does not upload, log in, or communicate with Bambu cloud services.
